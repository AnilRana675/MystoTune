# **MystoTune M6: Guided Setup Website and One-Click Render Deploy**

Feature PRD and TRD · builds on M5 (TRD v2.2) · October 20, 2026

## **1\. Summary**

Today a new user must fill in about 25 environment variables, run three terminal commands (npm run session, npm run channels, openssl), and make sure exactly one instance is running. Render’s free plan has no shell, and a Telegram session works best when it is created from the machine that will use it. M6 replaces that with three things:

1. A **setup website** served by the addon itself, which logs in to Telegram, picks channels, verifies everything and saves the configuration.  
2. A **Render Blueprint** and a Deploy button that create the web service and a Key Value store, and generate the secrets.  
3. A **session lease** in Redis, so two instances (for example during a deploy) can never use the same Telegram session at once.

**Outcome:** from the Deploy button to a playable track in under 10 minutes, with no terminal and no hand-typed secrets.

## **3\. Goals and non-goals**

**Goals**

* Zero terminal use on Render. Zero secrets typed by hand.  
* At most 5 values typed by the user in total (API ID, API hash, phone, login code, 2FA password if set).  
* Never lose the Telegram session to a duplicate instance.  
* No change in behaviour for existing .env users. Explicit environment variables always win.

**Non-goals**

* Multi-user accounts or a hosted service. Each person deploys their own copy.  
* Support for hosts other than Render and generic Docker/VPS in M6.  
* Telegram bot logins, or any admin features beyond a read-only status page and reconfiguration.  
* Automatic updates.

## **4\. Users and stories**

* **Render beginner.** I click Deploy, open one link from the logs, log in to Telegram in my browser, tick my music channels, and get a URL to paste into BitChord.  
* **VPS self-hoster.** I can use the same wizard in the terminal (npm run setup) or keep my .env as it is.  
* **Maintainer.** I can redeploy at any time without killing the Telegram session, and I can see which instance is active.

## **7\. Technical design**

### **7.1 Architecture**

Browser ──HTTPS──\> /{secret}/setup/\*  ┐  
BitChord ─HTTPS──\> /{secret}/manifest  │  one Fastify process  
                   /media  /art       ┘  
                        │  
          ┌──────────────┼───────────────┐  
     configStore       lease.ts        telegram.ts  
     (Redis blob or    (Redis SET NX)  (GramJS, ACTIVE only)  
      /data file)  
The setup code is loaded with a dynamic import() only in SETUP mode and released after finishing, so normal memory use does not grow.

### **7.2 Boot state machine**

| State | Entered when | Serves | Leaves when |
| :---- | :---- | :---- | :---- |
| BOOT | Process start | /healthz only | Configuration resolved |
| SETUP | No session in env or store | Empty manifest and search, /setup/\*, /healthz | Finish succeeds, then STANDBY |
| STANDBY | Configured, lease not held | Manifest, search from the snapshot. /stream and /media return 503 with Retry-After: 5 | Lease acquired |
| ACTIVE | Lease held and Telegram connected | Everything | Lease lost, SIGTERM, or auth failure |
| DRAINING | SIGTERM received | Existing streams finish for up to 10 s. New stream requests get 503 | Lease released, process exits |
| FAILED | AUTH\_KEY\_UNREGISTERED or an invalid session | /healthz unhealthy | Setup re-opens with a banner (“Your Telegram session expired”) and a new token in the logs |

/healthz must return 200 in STANDBY. Render keeps the old instance running until the new one passes its health check, and that is what makes the lease hand-over work (section 7.11).

### **7.3 Configuration resolution and derived secrets**

Order, highest first: **(1)** explicit environment variable, **(2)** encrypted config store, **(3)** profile defaults, **(4)** built-in defaults.

| Setting | On Render after M6 | On a VPS |
| :---- | :---- | :---- |
| APP\_SEED | Generated by the Blueprint | You generate once: openssl rand \-base64 32 |
| ADDON\_SECRET, MEDIA\_SIGNING\_KEY, CONFIG\_KEY | Derived from APP\_SEED | Derived, or set explicitly as today |
| PUBLIC\_BASE\_URL | From RENDER\_EXTERNAL\_URL | Required |
| PORT | Injected by Render | Default 8080 |
| REDIS\_URL | Wired by the Blueprint | Optional |
| PROFILE | render (FR-32) | vps |
| Telegram API ID/hash, session, channels, options | Entered in the wizard | Wizard, CLI or env |

Render’s generateValue produces a base64 256-bit value, which can contain /, \+ and \=. That is unsafe as a URL path prefix, which is why ADDON\_SECRET is derived as base64url instead of being generated directly.

import { hkdfSync } from 'node:crypto';

const seed \= Buffer.from(process.env.APP\_SEED\!, 'base64');  
const derive \= (info: string, len: number) \=\>  
  Buffer.from(hkdfSync('sha256', seed, 'mystotune/v1', info, len));

export const keys \= {  
  addonSecret: derive('addon-path', 24).toString('base64url'), // 32 URL-safe chars  
  mediaKey: derive('media-signing', 32),                        // 32 bytes  
  configKey: derive('config-store', 32),                        // AES-256-GCM  
};  
Rotating APP\_SEED changes the addon URL (re-add it in BitChord), invalidates all media tokens, and makes the stored config unreadable, so setup runs again.

### **7.4 Config store**

Plaintext, before encryption:

{ "v": 1, "apiId": 0, "apiHash": "", "sessions": \[""\], "channels": \["-100..."\],  
  "options": { "allowDownloads": 0, "monthlyBytesBudget": 4500000000 },  
  "updatedAt": "" }

* Encrypted with AES-256-GCM using CONFIG\_KEY and a random 12-byte IV. Stored as base64url(iv | tag | ciphertext) at Redis key cfg:v1, with no TTL.  
* Fallback on persistent disks: the same format at /data/config.enc, mode 0600\.  
* Every write is read back and decrypted to verify it before the wizard reports success.  
* The blob is below 4 KB. The phone number is never stored.  
* A durable backup is offered on the final screen: reveal the session string once (token required) so it can be saved as TELEGRAM\_SESSION\_STRING in Render, in case a free Redis plan loses data.

### **7.5 Routes**

The setup link printed in the logs keeps the token in the URL **fragment**, which browsers never send to the server, so it cannot appear in access logs or referrers:

\[setup\] open https\://\<service\>.onrender.com/\<secret\>/setup\#t=\<token\>

| Route | Method | Purpose |
| :---- | :---- | :---- |
| /{secret}/setup | GET | One self-contained HTML page (inline script and style, nonce-based CSP) |
| /{secret}/setup/api/unlock | POST | Exchange the token for an HttpOnly, SameSite=Strict cookie valid for 30 minutes |
| /{secret}/setup/api/creds | POST | Save API ID and hash |
| /{secret}/setup/api/login/phone | POST | Request the login code |
| /{secret}/setup/api/login/code | POST | Submit the code |
| /{secret}/setup/api/login/password | POST | Submit the 2FA password |
| /{secret}/setup/api/channels | GET | List channels and groups |
| /{secret}/setup/api/channels/count | POST | Audio count for one channel |
| /{secret}/setup/api/options | POST | Save options |
| /{secret}/setup/api/verify | POST | Run the checks and return results |
| /{secret}/setup/api/finish | POST | Persist, start, close setup |
| /{secret}/status | GET | Read-only status (FR-33) |

After finishing, every /setup/\* route returns 404\.

### **7.6 Telegram login**

The server creates one TelegramClient with an empty StringSession, floodSleepThreshold: 0 and connectionRetries: 3, and calls client.start() with callbacks for phone, code and password. Each callback is a pending promise that the matching HTTP endpoint resolves. A 5-minute idle timer disconnects the client and discards the state. If Render spins the instance down mid-login, the user simply starts the login again. Traffic from the open page keeps it awake.

| Telegram error | Message shown | Next step |
| :---- | :---- | :---- |
| API\_ID\_INVALID | The API ID and hash do not match | Re-check at my.telegram.org |
| PHONE\_NUMBER\_INVALID | That phone number is not valid | Use international format, for example \+977… |
| PHONE\_CODE\_INVALID / PHONE\_CODE\_EXPIRED | The code is wrong or expired | Request a new code |
| SESSION\_PASSWORD\_NEEDED | Two-step verification is on | Show the password field |
| PASSWORD\_HASH\_INVALID | Wrong password | Retry, no lockout from our side |
| FLOOD\_WAIT\_X | Telegram asks you to wait X seconds | Show a countdown |

QR login (signInUserWithQrCode in GramJS) is a P2 alternative. Verify that the installed GramJS version exposes it before committing.

### **7.7 Channel picker**

getDialogs({ limit: 200 }), filtered to channels and groups, returns titles and ids in the \-100… form. The audio count is fetched on demand with messages.Search and InputMessagesFilterMusic (limit 1, reading the total), at most 3 in parallel with a short delay, to avoid FloodWait. Channels with zero audio get a warning but can still be selected, because FLAC sent as plain documents may not match the music filter.

### **7.8 Verification checks**

| Check | Passes when | If it fails |
| :---- | :---- | :---- |
| Redis | PING under 200 ms | Warning only. On Render, show the session backup instructions |
| Config store | Write, read back and decrypt | Block finish |
| Telegram | getMe succeeds | Return to login |
| Channels | Each channel returns a page of messages | Offer to remove it (not joined or protected) |
| Audio | At least one audio file per channel (music filter or document scan) | Warn: check this is the right channel |
| Public URL | The server fetches its own PUBLIC\_BASE\_URL/{secret}/manifest.json and finds the addon id | Show how to fix PUBLIC\_BASE\_URL |
| Lease | Acquired, or a clear message that another instance holds it | Explain and wait |
| First sync | Starts, with progress | Continues in the background |

### **7.9 Finish**

1. Persist the config (verified write).  
2. Move SETUP to STANDBY, then to ACTIVE once the lease is held and Telegram connects.  
3. Start the indexer. Restore the Redis snapshot first if one exists.  
4. Close setup. The final screen shows PUBLIC\_BASE\_URL/{ADDON\_SECRET} with a copy button, and the BitChord steps: Settings → Sources → Add an addon.

### **7.10 Render Blueprint**

services:  
  \- type: web  
    name: mystotune  
    runtime: docker  
    plan: free  
    region: singapore  
    healthCheckPath: /healthz  
    autoDeploy: false  
    envVars:  
      \- key: APP\_SEED  
        generateValue: true  
      \- key: REDIS\_URL  
        fromService:  
          type: keyvalue  
          name: mystotune-kv  
          property: connectionString  
  \- type: keyvalue  
    name: mystotune-kv  
    plan: free  
    region: singapore  
    ipAllowList: \[\]  
Based on Render’s Blueprint documentation:

* generateValue: true creates a base64 256-bit secret.  
* sync: false prompts only at the first Blueprint creation, so it is not used for anything that may change.  
* fromService with keyvalue exposes a connectionString.  
* RENDER\_EXTERNAL\_URL holds the public URL. If it is not set automatically, wire it with fromService and envVarKey.  
* autoDeploy: false stops every git push from redeploying, which also avoids needless instance overlap. Deploy when nobody is listening.

Validate the file against render.com/schema/render.yaml.json and confirm your account has a free Key Value plan. The Deploy button link has the form https\://render.com/deploy?repo=https\://github.com/AnilRana675/MystoTune (verify the current format).

### **7.11 Session lease and two-instance safety**

Two processes using one Telegram session make Telegram invalidate it (AUTH\_KEY\_DUPLICATED), and the addon stays dark until a new login. This happens during ordinary deploys, because the old and new instances overlap.

**Algorithm** (key lease:session:{slot}, value instanceId, slot 0 by default):

* **Acquire:** SET key id NX PX 45000, polled every 5 s while in STANDBY.  
* **Renew:** every 15 s with a compare-and-extend script (Appendix). A failed renew for 30 s makes the instance **self-fence**: it stops all Telegram I/O and drops to STANDBY before the lease can expire.  
* **Release:** on SIGTERM, enter DRAINING, wait up to 10 s for active streams, disconnect Telegram, then run a compare-and-delete.  
* instanceId is RENDER\_INSTANCE\_ID if present, otherwise the hostname plus 4 random characters.

**Deploy overlap, step by step**

1. The new instance boots in STANDBY and passes /healthz.  
2. Render stops routing to the old instance and sends it SIGTERM.  
3. The old instance drains, disconnects and releases the lease.  
4. The new instance acquires the lease within about 5 s, connects, and becomes ACTIVE.

Target gap: 15 s or less on a graceful deploy, and at most 60 s after a crash (lease TTL plus polling). Check Render’s SIGTERM grace period. If it is shorter than the drain time, shorten the drain.

**Without Redis,** the lease cannot work. The M5 behaviour stays as the fallback (retry AUTH\_KEY\_DUPLICATED at boot, then exit), and the verification screen warns about it.

**What is shared and what is not when two instances run**

| State | Scope | Consequence |
| :---- | :---- | :---- |
| flood:until, bytes:month, rate-limit counters, snapshot | Shared in Redis | Budget and cooldowns hold across instances |
| Admission control (concurrent streams) | Per instance | Effective concurrency can double during an overlap |
| Document LRU, head-window cache, SQLite index | Per instance | Warm-up is repeated, nothing breaks |

**Two sessions (FR-35, P2).** The wizard can log in a second time and store both strings. Each instance claims the first free slot, so two instances can both be ACTIVE with no gap. Both logins appear in Telegram’s active-sessions list, and both share the account’s FloodWait limits.

**Two Render accounts.** Run them as two separate BitChord sources, each with its own session, Redis and Blueprint. BitChord moves to the next source on a 404, so when one source hits its MONTHLY\_BYTES\_BUDGET the other takes over. They cannot share a lease, since Render Key Value is private to its account, so they must never share a session string. Check Render’s terms before creating a second account.

## **8\. Security**

| Threat | Mitigation |
| :---- | :---- |
| Setup token leaks into logs or referrers | Token in the URL fragment, exchanged by POST, removed with history.replaceState |
| Brute-forcing the token | 144-bit random token per boot. 5 failures lock the IP for 15 minutes. Global cap of 20 unlock attempts per hour |
| Setup left open | Closes after finish. Status page warns if SETUP\_ENABLED=1 |
| Session theft from Redis | AES-GCM with a key that exists only in Render’s environment. Key Value is internal-only (ipAllowList: \[\]) |
| Secrets in logs | Redaction of phone, code, password, session and API hash. Never logged |
| XSS | One inline script with a nonce, default-src 'none', connect-src 'self', no third-party code, textContent only |
| CSRF | SameSite=Strict cookie, custom header, Origin check |
| Clickjacking | frame-ancestors 'none' |
| Misuse of the login page | A banner states that this page signs in to a Telegram account, and recommends a dedicated account |
| Memory remnants | Login state cleared on finish, timeout or error |

## **9\. UX specification**

Mobile first (360 px wide), one task per screen, plain language, no jargon.

1. **Welcome:** what the page does and a checklist: a dedicated Telegram account that has joined your music channels, and an API ID and hash from my.telegram.org.  
2. **API credentials:** two fields and a link with steps.  
3. **Login:** phone, then code, then password (only if needed), with a countdown for resends.  
4. **Channels:** searchable list with checkboxes and a “Count audio files” button.  
5. **Options:** the preset is shown as a summary (downloads off, 4.5 GB monthly budget, Singapore), with an Advanced section.  
6. **Verify:** live rows with a spinner, a green tick or a red cross, and a one-line fix.  
7. **Done:** addon URL, copy button, BitChord steps, a session backup, and a reminder that setup is now closed.

Every error states what happened and what to do next.

## **Appendix A. Lease scripts (Redis Lua)**

\-- renew: KEYS\[1\]=key, ARGV\[1\]=instanceId, ARGV\[2\]=ttlMs  
if redis.call('get', KEYS\[1\]) \== ARGV\[1\] then  
  return redis.call('pexpire', KEYS\[1\], ARGV\[2\])  
end  
return 0

\-- release: KEYS\[1\]=key, ARGV\[1\]=instanceId  
if redis.call('get', KEYS\[1\]) \== ARGV\[1\] then  
  return redis.call('del', KEYS\[1\])  
end  
return 0
